## Finding R36-1 — in-flight old-session Pi output can enqueue after peer has switched sessions

**Location:** `lantern/ws.py:433-487`, `WebSocketHub.broadcast()`.

**PLAN invariant**

For a peer switching session A -> B:
- peer no longer receives A output;
- output events are isolated by exact sessionId + generation;
- after B attach completes, the peer's active Pi attachment is B.

**Current broadcast flow**
1. `broadcast(terminal_output A)` acquires `hub.lock`;
2. while peer is still attached to A, it snapshots:
   - `peers`;
   - `pi_payloads[peer] = pi_session_output(A)`;
3. releases `hub.lock`;
4. before `peer.send(pi_payload)`, another thread can complete A -> B attach;
5. peer is now authoritatively attached only to B;
6. old broadcast still uses its stale `pi_payloads` snapshot and sends A output to the peer.

There is no final session/generation/attachment revalidation at the queue-enqueue boundary for Pi output/exit payloads.

## Fresh deterministic reproduction

REVIEW used:
- real `PiSessionRegistry`;
- real `TerminalManager`;
- real `WebSocketHub/dispatch`;
- fake PTY I/O only.

Sequence:
1. peer attaches A;
2. A emits `A-IN-FLIGHT`;
3. broadcast reaches the peer's Pi-output send boundary and is paused before enqueue;
4. while old A send is paused, the same peer successfully attaches B;
5. B replay is queued and hub truth says peer is attached to B;
6. old A output send resumes.

Fresh observed message order:

`messages [('pi_session_replay', 'b', 0, None), ('pi_session_output', 'a', 1, 'A-IN-FLIGHT')]`

The proof assertion failed:

`old-session output queued after peer switched to B`.

So after successful B initialization the peer still receives a stale A output frame.

## Why this is material

This is not merely a pre-switch in-flight frame that was already queued.

The old A frame is actually enqueued **after** the B switch and B replay have completed.

The client therefore observes cross-session traffic in this order:
1. B replay / B is active;
2. A output arrives afterward.

That directly violates:
- one active Pi attachment per peer;
- session switch isolation;
- A-output-does-not-reach-B-only peer behavior.

The same stale-snapshot pattern also applies to `pi_session_exit`.

## Required correction

Revalidate Pi event delivery against current authoritative attachment state immediately before queue enqueue.

Minimal acceptable direction:
- for a computed `pi_session_output` / `pi_session_exit`, before `peer.send()`:
  - verify under `hub.lock` that `pi_peer_session[peer]` still equals payload sessionId;
  - route still has the same generation;
  - peer remains in that route's peer set;
- make that validation ordered with the queue enqueue so a completed session switch cannot occur between validation and enqueue.

A validation followed by unlocked send has the same TOCTOU shape already encountered for ownership notices.

Use the existing per-peer ordering/queue primitive or an equivalent narrow enqueue guard; do not hold hub lock over actual socket I/O.

Required guarantee:
- once B attach/replay has been queued as the peer's active session initialization, no A Pi output/exit may be queued afterward;
- output that was already queued before the switch may remain in normal FIFO order;
- other A peers still receive A traffic;
- B traffic remains unaffected;
- no output duplication/loss for peers that stay attached to A.

Add deterministic regression matching the reproduction:
1. A output broadcast snapshots peer while attached A;
2. pause before peer enqueue;
3. same peer completes switch to B and receives B replay;
4. resume old A broadcast;
5. assert no A output/exit is queued after the B replay;
6. assert an A peer that did not switch still receives the A event.

Also cover `pi_session_exit` if the fix shares the same delivery helper/path.
